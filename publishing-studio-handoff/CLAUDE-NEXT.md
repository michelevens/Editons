# What's left — instructions for Claude Code

`prototype/index.html` is finished. It covers the UX, copy, flows and edge cases for all 31 screens, and HANDOFF.md documents each one. This file lists only the work a browser prototype **can't** do: real services, real data, real security. The prototype stands in for each with a stub. Replace every stub with the real thing below and keep the UX the same.

Use the prototype as the acceptance test. Port `crawl.js`-style coverage (every `[data-a]` control works, zero console errors) and the scripted flows listed in HANDOFF.md to Playwright against the real app.

---

## 0. Ground rules
- **Behavior:** match `prototype/index.html` exactly for behavior, copy and validation messages. Match `reference/mockup.png` for the Writing Studio visuals.
- **Service boundary:** each external integration sits behind a service interface with a fake implementation for tests. That way the prototype's stubs map one-to-one onto adapters.
- **Every action that costs money or credits:**
  - Create a job record first and debit credits atomically.
  - Run the job on a queue.
  - Refund the credits if it fails.
  - Report progress to the UI (the prototype's progress bars).
- **Secrets:** stored only in a secrets manager. No keys in the client.

## 1. Backend foundation
- **Stack:** pick one and record it in `CLAUDE.md`. The default is TypeScript end to end (Next.js or Vite + a Node API), Postgres with Prisma or Drizzle, Redis plus BullMQ for jobs, and S3-compatible object storage.
- **Data model:** derive it from the prototype's state. `BOOKS[].data` gives parts, chapters, suggestions, agents/findings, comments, research and terms. Also model `ACCT`, `TEAM`, `CLIENTS`, `INTEG`, `NOTIFS`, `TICKETS`, `LOG`, plus a revisions table for chapter versions. Multi-tenant by workspace, with row-level access checks on every query.
- **Audit log:** an append-only table written by the API layer, never by the client. It powers the Audit Log page and the CSV export.

## 2. Authentication & accounts
- **Sign-in:** real email/password (argon2id), email verification, password reset with single-use tokens that expire in 30 minutes, and Google OAuth. Sessions in httpOnly secure cookies.
- **Two-step verification:** TOTP (RFC 6238) using the setup-key flow from the prototype, plus 8 hashed single-use backup codes.
- **Account settings:** session list with remote sign-out; a password change revokes other sessions. Account deletion is a soft delete, then a hard delete after 30 days, and data export is available before deletion.
- **Abuse protection:** rate limits on auth endpoints, plus lockout and a CAPTCHA after repeated failures.

## 3. Editor persistence & real-time collaboration
- **Storage:** the prototype keeps the manuscript as HTML strings. Store a structured document instead (TipTap/ProseMirror JSON).
- **Co-editing:** real-time with Yjs (Hocuspocus, or Liveblocks if you'd rather buy it). Includes presence avatars and live cursors, replacing the prototype's static `PRESENCE`.
- **Revisions and tracked changes:** server-side revision snapshots on save (Version history). Tracked changes become a suggestion mode (TipTap collaboration-suggestions or a custom mark), replacing the prototype's diff-since-baseline.
- **Chapter locks:** enforced server-side, not only in the UI.
- **Comments and @mentions:** stored and fanned out to notifications (in-app plus email, following `PREFS`).

## 4. AI (replaces every templated generator)
Call the Anthropic Claude API from the server only.
- **Review agents** (7 core plus 4 specialists):
  - One prompt per agent.
  - Structured JSON output: `{findings:[{text, chapterId, anchorText, severity, suggestedRewrite?}]}`.
  - Anchor each finding to document positions so "Show in text", Apply and Dismiss work on the real document.
  - Strictness (Light, Standard or Strict) changes the prompt.
- **Inline suggestions:** the AI Suggestion popover is generated by the Line Editor agent.
- **Voice profile:** keep the prototype's measured stats and add an LLM style summary. Score edits against the profile before showing them.
- **Generators:** the course (objectives, quizzes), Marketing Kit (description, email, posts) and translation should each be a prompt with the book as context. Translations go chapter by chapter, with the glossary (`TERMS`) passed in so terms stay consistent.
- **Cost controls:** meter real token use against the `COST` table, cache unchanged chapters, and cap the context size.
- **Clinical/Legal reviewers:** label the output as assistance, not professional advice. That copy is already in the prototype.

## 5. Billing (Stripe)
- **Products:** Free, Author ($19) and Studio ($79) as Stripe Products/Prices, plus 500/2,000 credit packs as one-time Prices.
- **Payments:** Checkout and the Customer Portal for card updates. The prototype's "Update payment method" modal hands off here.
- **Webhooks:**
  - `checkout.session.completed`, `customer.subscription.updated/deleted` and `invoice.paid` drive plan state and the credit ledger.
  - Prorated upgrades come from Stripe's proration, not client math.
  - Credits reset on each paid renewal invoice.
- **Invoices page:** reads Stripe invoices.
- **Plan limits:** enforce books, seats, formats and feature tiers on the server (the prototype enforces them client-side).

## 6. File generation
- **PDF (print):** an HTML-to-PDF engine with paged media. Prince or DocRaptor give the best results; Paged.js plus headless Chrome is a free option. Use the Design page settings (trim, margins, font, size, leading, drop caps, running heads), embed fonts, and add bleed where needed. Validate against KDP/IngramSpark PDF requirements (PDF/X-1a for Ingram).
- **Large print:** same pipeline at 18 pt.
- **EPUB 3:** generate the package and run **epubcheck** in CI and on every export. Run **DAISY Ace** for the Accessibility page and include the a11y metadata the prototype shows.
- **DOCX:** docx library or Pandoc. **Markdown/HTML:** direct.
- **Delivery:** finished files go to object storage with signed download URLs. This replaces the prototype's preview modal, which exists only because artifacts can't download.

## 7. Audio (Audiobook Studio)
- **Narration:** a TTS provider with the 4 voices mapped to provider voices. The pronunciation dictionary becomes SSML/phoneme overrides.
- **Mastering:** ffmpeg to ACX spec (192 kbps CBR MP3, 44.1 kHz, RMS −23 to −18 dB, peak ≤ −3 dB, noise floor ≤ −60 dB, room tone at head and tail). Validate every file before "Export for ACX".
- **Previews:** short server-rendered samples, replacing browser `speechSynthesis`.

## 9. Security, privacy, compliance
- **Security:** OWASP ASVS L2 baseline. CSP, CSRF protection, input sanitization on all manuscript HTML (DOMPurify server-side), and file-upload scanning for images and imports.
- **Legal documents:** Privacy Policy, Terms of Service, DPA, cookie consent where required, and a subprocessor list. **You must supply or approve these.**
- **HIPAA:** manuscripts aren't PHI by default. Add a terms clause forbidding patient-identifiable data, rather than taking on HIPAA scope.
- **Backups and recovery:** daily backups with point-in-time recovery, plus a documented restore drill.

## 10. Operations
- **Pipeline:** CI (lint, typecheck, unit, Playwright parity suite, epubcheck) → preview environments → production.
- **Monitoring:** Sentry, structured logs and uptime checks. Alert on job failures, webhook failures and credit-ledger drift.
- **Load testing:** concurrent editors per chapter, export queue throughput, AI job concurrency.
- **Analytics:** product analytics events for onboarding completion, first export, first publish and upgrades.

## 11. Decisions only the owner can make (ask, don't guess)
1. Final pricing and the credit cost per action, once real AI and TTS costs are known.
2. TTS provider and voice licensing (commercial audiobook rights).
3. PDF engine (Prince license vs. open source).
4. Which stores to support at launch.
5. Whether to pay co-authors through the platform (money transmission, Stripe Connect) or only report splits.
6. Brand name and domain. "pubstudio.site" in the prototype is a placeholder.

## Suggested build order
1 → 2 → 3 (core writing works for real) → 6 (exports) → 4 (AI) → 5 (billing) → 7 → 8 → 9/10 hardening. Ship a private beta after step 5.
